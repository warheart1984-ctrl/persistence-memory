# CL_CHAOS_100x: report of the run on 2026-10-07

One smoke round, then 100 rounds, against a throwaway clone of the stack (project `jarvis-chaos100x`, containers `chaos100x-*`, port
18017, its own volumes, images, network, random secrets and test keys). The live stack (`127.0.0.1:8011`, `jarvis-db`, `jarvis-app`) was
never contacted by the hammer, which refuses it (exit 3, checked: `--target http://127.0.0.1:8011` is refused before any request); afterwards the
live containers had the same uptime (18 h, healthy), the same image ids, `/ready` was fine, and `~/jarvis-ledger/keys` still does not exist.
`--i-know-this-is-live` was never passed. Raw numbers: `results-2026-10-07.json`; the smoke round: `sample-smoke-round.log`.

**49 probes per round; 100 rounds = 4900 probe runs. Result: 4900 PASS, 0 FAIL, 0 ERROR, 0 SKIP, 0 unexpected 5xx.** Seed `82840ae4`,
10 019 s (2 h 47 min). The ledger was empty when the stack was built; the three smoke rounds that preceded the run are in the totals below.

## What happened first (the hammer was wrong before the ledger was)

The probes were first run in-process against a throwaway schema, then in three smoke rounds on the stack. Every failure there was found
and fixed before the 100 rounds; none was hidden:

* **An application bug, found and fixed in this change.** A NUL byte in a path (`GET /api/jarvis/memory/mem-%00`) or in a JSON text field
  (`"content": "a\u0000b"`) answered **503 "Ledger store unavailable"** and logged an outage: PostgreSQL text cannot hold NUL, the store turned
  the driver's `DataError` into "unavailable", and the caller's mistake looked like an outage. It is now a **400 `invalid_input`**
  (`app/store_errors.py`, `app/pg_store.py`, `app/main.py`, `tests/test_nul_input.py`, both directions mutation-checked). Other database errors are
  still a 503. A query-string NUL on retrieve was never a problem (matching is done in Python): that is D2's "no match, no error".
* **Probe expectations that were mine to get right:** a *fact* may cite only a *fact* evidence object (A4 first cited a decision object and
  Clause V correctly refused it); the replay routes name the error in `detail`, not in a `code` field (F3); a bad signature on a block that is
  already attested is an equivocation, a 409, not a 422 (G5); an unreadable roots file makes the offline tool *refuse* (`trust_roots_unreadable`,
  exit 2), which is stricter than the "not verified" warning an empty file gives (G6 now checks both and `require`); an existing key file made
  `ssh-keygen` wait for a yes/no and the probe hung (G4, now unique names and no stdin).
* **An environment fact:** the database image's `pg_hba.conf` lets the application and migrator roles into the `jarvis` database only, so a
  scratch database could not be verified from another container. F6 adds one temporary rule on the *throwaway* database container for the
  scratch database and always takes it out (final check: 0 rules, 0 scratch databases left).

## Where the ledger ended

History 4 326 entries (126 before the run: the smoke rounds), 3 026 blocks (1.4 entries per block: the probes seal in tiny batches on purpose),
4 017 records, 412 evidence objects, 103 receipts, 3 207 attestations (3 001 blocks, 103 receipts, 103 checkpoints), 205 trust statements,
103 authorized keys (the test signing key and one short-lived key per round, each revoked). Database 22 MB; the 6 000-entry cap was not reached.
The final checks all passed: history chain, blocks, signing log (25 blocks unsigned because they were sealed after the last signing pass),
all 103 receipts re-derived, `jarvisctl verify` in the throwaway stack exit 0 ("blocks intact: 3026 block(s) sealed through seq 4326, 0 entries
unsealed"), schema still v7, no scratch database and no temporary pg_hba rule left.

## Anything unexpected

1. **Cost grows linearly with the ledger.** Round time 60 s → 143 s; retrieve with a hostile string (D2) 357 ms → 3.9 s; `blocks/verify`
   89 ms → 1.5 s; receipt re-derivation through the service 67 ms → 1.8 s; the scratch tamper-and-verify (F6) 19.5 s → 50 s; the signer pass
   12 s → 33 s. Retrieval loads the records and matches in Python, and the verifiers walk everything, so a ledger of a few thousand entries is
   already felt under concurrency (the flood probe above). The application container's memory went from 76 MiB (after one smoke round) to
   279 MiB at the end; one run cannot say whether that is caching or a leak.
2. **The existing rehearsal script names the live stack.** `deploy/mint/rehearse/scenario.sh` hard-codes `jarvis-db` / `jarvis-app` and runs
   `docker kill jarvis-db` and `docker rm -f ... jarvis-db jarvis-app`; run from this repository it would act on the live containers. The
   throwaway clone leaves that directory out and its copy-time check refuses any other live name. The script itself was not changed.
3. The live stack reports no `stack` identity in `/ready` (it runs an older build), so the hammer refuses it for that reason as well as for its
   port; once this build is deployed the compose default makes it report `jarvis-live`.

## What the run could not test

`require` mode (warn only, as asked); L2 (nothing cosigned a checkpoint); the hardware-root and PC witness paths; backups, restores, the drill and
the offsite copy; the OAuth/MCP surfaces and the AMUL, RAG and LLM routes; network failure (one machine, loopback), a full disk, or a crash of
the *application* container (the database was stopped and started; the app was not killed); memory or CPU limits like the Mint box's (the
figures describe this host); anything about the live deployment, which stayed at v6 and unsigned.
